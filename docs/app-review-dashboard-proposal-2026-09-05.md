# アプリレビューとダッシュボード設計のたたき台

作成日: 2026-09-05 / 更新: ダッシュボードの実装へ進む承認を受け、`/dashboard` を追加。以下のレビュー・設計案のうち、実装範囲と確認結果は [dashboard-verification.md](dashboard-verification.md) を参照。その他の改善提案は未実装。

## 確認範囲と総評

ローカルの HEAD `056a7fe` を対象に、入力、レシート、一覧、月次・年次集計、データ型と取得処理を確認した。公開環境・実際の蓄積データ・スマホの実機表示は未確認。以下ではコードで確認できる挙動と設計提案を区別する。

既に、カメラの連続撮影・OCR・下書き、共通入力部品、電卓、店舗候補、定期取引、月次カテゴリ内訳から明細への導線、年次の収入・支出・差額切り替えがある。日々の記録と精算の土台は整っている。改善の優先順位は、入力の一貫性、集計の信頼性、増減理由を探せる分析の順がよい。

## カメラ登録について

2026-08-03 の `056a7fe` は「レシート確認画面を取引入力フォームと共通化」。現在の `ReceiptCaptureModal` と `TransactionModal` は同じ `TransactionFormFields` を使用し、支出選択時に家庭向け立替のチェックボックスを表示する。チェックすると共通変換処理で `type=advance / advanceToUserId=null` として保存する。

そのため、報告された「カメラにはチェックボックスがない」は現在のコードだけでは再現を確認できない。公開版のコミット、画面で選択中の種別、スクロール位置を確認する必要がある。公開版への未反映が原因だと断定はしない。既存のカメラテストは入力表示・立替タブ切り替えを確認するが、家庭向け立替のチェックから保存までを直接検証していない。

### 望ましい登録体験

撮影・画像選択 → OCRの値を入れた通常登録フォーム → 内容を確認して登録。

- 金額、日付、カテゴリ、支払者、家庭向け立替、店舗、メモを通常入力と同じ順序・同じ意味で扱う。
- カメラ固有の要素は画像の参照、読み取り状態、下書きの切り替えにまとめる。
- スマホでは画像を折りたたみ、下書き一覧は「未登録3件」から開く。入力フォームを先に見せる。大画面では画像とフォームを横に並べる。
- 支払者と立替設定を隣接させ、チェックの見出しを「家計の支出を自分のお金で立て替えた」、補足を「あとで世帯と精算」にする。「自分」以外を選べる場合は支払者名に追従させる。
- 保存前に「○○さんが支払い／世帯とあとで精算」などの結果を短く表示する。
- 通常入力と同様に「登録して閉じる」「登録して次へ」を用意し、最後の1枚では閉じる操作を主にする。
- 読み取りが不確かな欄には色だけでなく「要確認」を表示し、修正しやすくする。OCR失敗時の手入力・再解析という既存機能は維持する。

### 入力の意味を整理する案

現状は「支出＋家庭向け立替チェック」と「立替＋家庭全体に立替」の2経路で同じ内容を登録できる。短期はチェックボックスと支払者の見やすさを改善する。中期には表示上の区分を「家計の支出」「個人間の立替」「収入」とする案がある。家計の支出内で精算要否を選び、データ上の会計ルールは維持する。ナビゲーション変更を伴うため、これは別途判断する。

## ダッシュボードの目的と配置

目的は「今月はいくらか」に加えて、「いつもと比べてどうか」「どこで増えたか」「どの記録か」に答えること。概要の既存配置は維持する。

| 案 | 良い点 | 課題 | 推奨 |
| --- | --- | --- | --- |
| 既存の4タブにダッシュボードを追加 | 発見しやすい | スマホで5タブが混雑。月次・年次と役割が重複しやすい | 小規模に試す場合 |
| 独立したダッシュボードページ | 概要を維持し、分析用の期間や絞り込みを持てる | 概要から分かりやすい入口が必要 | 第一候補 |

独立ページへ概要上部の「ダッシュボード」から入る。戻った際は概要の年月を保持する。分析側の選択年月・カテゴリはURLに保持する設計が候補。下部の撮影・支出・立替・収入は記録用アクションとして役割を維持する。既存の年次ビューは初回導入時には残し、統合判断は利用後に行う。

## 初期版の画面構成

1. 対象月と比較期間。初期表示は今月、比較は前月同日まで。過去月は前月全期間と比較する。
2. 小さな指標を最大3つ。「家計の支出」「比較期間との差額」「記録上の収支」。差額は金額を主にし、割合は補助とする。
3. 対象月の利用ペースの折れ線グラフ。日別・週別の利用額を切り替え、支出が集中した日や週を確認する。追加提案として「累計」に切り替えると前月の同じ日付までと比較できる。通常は日別を初期表示する案。
4. 直近6か月の家計支出の棒グラフ。月を押すと対象月が変わる。収入・支出の同時比較は必要なら追加する。既存年次グラフの累計と月次を同じ軸に重ねる方式は、累計が大きくなり月次差が小さく見えるため、このページでは避ける。
5. カテゴリ別の当月・比較期間の横棒と増減額。額の大きい順／増加額の大きい順を切り替えられる。円グラフは既存概要にあるため、こちらは比較を優先する。
6. カテゴリを選ぶと同ページ内で対象取引を表示。日付、店舗またはメモ、金額、支払者、精算区分、レシートを確認できる。閉じても期間・スクロール位置を失わない。

スマホは指標→対象月の利用ペース→月ごとの推移→カテゴリ比較→明細の縦並び。大画面でも利用ペースは横幅を使い、その下に月ごとの推移とカテゴリ比較を横に配置可能。サンプル画面の数値は架空であり、実際の家計評価を示さない。

### 対象月の利用ペース（2026-09-05の壁打ちを反映）

ユーザーから「既存例に加えて、対象月の日別・週別の利用額を折れ線で見たい。どこで増えたかはカテゴリで確認できる」との提案があった。利用ペースを初期版の構成に加え、カテゴリ比較も維持する。その後の実装承認を受け、この構成をアプリに追加した。

- **日別**: 横軸は対象月の日付、縦軸はその日だけの家計支出。記録のない経過日は0円とし、未来の日には値や線を置かない。日付を押すと金額を確認する。時刻は既存の発生日データにないため、時間帯別は対象外。
- **週別**: 月曜〜日曜で合算。月初・月末は対象月内だけを含め、「8/1〜2日（2日間）」のように期間と日数を明示する。月をまたぐ支出を含めないため、日別・週別合計と対象月の総額が一致する。
- **週の途中**: 今週は今日までで集計し「途中・○日分」と表示する。未到来の週に0円の点を置かない。2日間と7日間の週を同条件として増減評価しない。初期案では週別に前月の線は重ねない。
- **累計（追加提案）**: 月初からの家計支出の積み上がりを、対象月は実線、前月は破線で表示する。日別額・週別額とは別の表示モードにして軸の意味を明示する。現在月は当月・前月とも比較可能な同日までを描画し、前月に存在しない日付以降は前月の線を止める。前月の最終値を架空の31日目へ伸ばさない。
- **操作**: 日別・週別・累計を切り替えても対象月を保持。月次棒グラフや対象月の選択変更に連動する。金額確認はタップとキーボードの両方で可能にする。日・週から取引一覧への絞り込みは後続の追加候補とし、現在の画面案は金額の確認まで。
- **読解**: 定期支出も家計支出として含むため、支払日には山が生じる。山や前月超過だけで「使いすぎ」と断定せず、カテゴリ比較と合わせて振り返る。

画面案は終了した2026年3〜8月のサンプル。日別データは架空で、各月の日別合計・週別合計・累計最終値が既存サンプルの月額に一致する。現在月の未到来日・途中週の表示は設計ルールであり、このサンプルでは再現していない。

## 集計ルールの設計

- 家計支出 = 通常支出 + 世帯向け立替。個人向け立替は除外。精算は返済なので再度支出に加算しない。既存の `isHouseholdExpense` と整合させる。
- 収支 = 記録済み収入 − 家計支出。「口座残高」「貯蓄額」とは表記しない。
- 日付は発生日を使用。途中月は対象日数を明示し、前月同日までと比較。前月に存在しない日は末日で止め、日数差を表示する。
- 比較元が0円なら増減率は「—」、増減額は表示。「無限大」「100%増」としない。
- 未来月は未到来、取引ゼロの月は「記録なし」。ゼロ支出と入力漏れを自動判別できるとはしない。
- カテゴリ未設定は「未分類」に含め、カテゴリ合計と家計支出合計を一致させる。
- 店舗未設定は「未入力」として残し、店舗がある取引だけで家計全体を代表させない。
- 定期支出は実際に登録された取引を実績として集計。予定額と二重に足さない。自動生成前の月は実績が不足し得るため、予定の表示は実績と分ける。
- 未登録のレシート下書きは実績に含めず、必要なら対象期間を断定しない未登録件数を併記する。
- 支払者が不明な古い記録も「不明」として合計に残す。
- 全期間の累計未精算残高を、選択月の未精算額として表示しない。取引単位の消込関係は現在のモデルから保証できないため、取引ごとの「精算済み」ラベルは別途設計する。

## 実装判断時の見込み

基本の月次推移・カテゴリ比較・明細表示は、金額・発生日・カテゴリ・支払者・店舗が既にあり、データ項目追加なしで設計できる。Recharts、期間取得、カテゴリ明細にも再利用できる基盤がある。ただしこれは設計上の見込みであり、実装や見積もりの確定ではない。

先に件数上限・未分類データ・既存集計との一致を確認する。期間と世帯を指定したDB集計を採用する場合は、新規マイグレーションと世帯権限の検証が必要。件数が少ない初期試作なら、上限を超えても漏れないページングを実装した取得で集計する選択肢もある。店舗名の名寄せ、正確な固定／変動分類、予算、精算の取引別消込には追加設計が必要。

### 実装前の受け入れ条件案

- 手入力・カメラ入力とも、家庭向け立替を最初の保存で登録できる。通常支出と個人向け立替も正しく区別される。
- Aのレシートを修正してBへ移動し、Aへ戻っても入力が保持される。
- カテゴリ未設定の支出があっても総額と内訳が一致する。
- 1,001件以上の期間でも全件を含む集計になる。
- 月途中、前月0円、2月と31日月、記録なし、未来月の表示が誤解を招かない。
- 日別合計・月内の週別合計・累計の最終値が、対象月の同じ日までの家計支出合計と一致する。
- 月またぎの週、途中週、月曜日に始まる月、前月より長い月を正しく扱い、対象月以外の取引を週別合計へ混ぜない。
- グラフから明細を開いたとき、同じ期間・同じ家計支出条件で金額が一致する。
- 更新・削除後は対応する比較値と明細が更新される。
- 360px幅で主要操作が押せ、色やホバー操作だけに頼らない。

## 壁打ちしたいこと

利用ペースを追加し、増減の内訳はカテゴリ比較で確認する方向を反映した。日別／週別／累計の切り替えと月曜始まりの週区切りを実装し、利用者の動作確認後にマージ・デプロイを判断する。
